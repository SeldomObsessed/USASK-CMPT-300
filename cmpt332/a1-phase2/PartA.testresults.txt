Summary:

It seems that the program can detect invalid parameters for the most part.
The only addition that needs to be done is to do a check for a large deadline
parameter, as we dont want the user to be able to let execution sleep for an
unreasonably long time.

The more concerning part is the seg fault that occurs when executing with valid
parameters. Upon further investigation it would seem that the seg fault occurs
when calling Sleep(deadline*100). Inspecting execution using gdb shows that the
argument is valid, but there is a Macro defined function that returns a null
pointer which when dereferenced causes the seg fault. No idea why this is
happening as this is function and execution goes through an archived library
file for the UBC threads package.

Conclusion:

The structure of partA1->partA4 fortunately uses the same function that detects
invalid parameters. This would mean that testing each remaining part would
yield the exact same results. It would be pointless to repeat certain tests
due to this. Instead we can repeat the failed tests on partA1 and partA3,
as they have been roughly fully implemented. partA4 is still skeleton code.

  Failed -> now why would the number of square invocations be different? It
is not that the invocations of square would change, it is more likely the case
that not all instances of the invocation of square() are being properly
recorded. This is likely the result of different thread executions accessing
the square() counter concurrently, and undoing work. A mutual exclusion tool
would solve this.

Conclusion:

  It would seem that the code is non-deterministic in result. This is not
useful, but it is worth studying. The most disappointing part however, is the
fact that the threads are executing too fast to relay a significant measurement
of their speed. A more precise measurement tool would be useful in analyzing
thread execution speed. When walking through the code in gdb, it has been
witnessed that at lower Param 3 executions (0-1000), threads that are created
in a loop will finish execution before the next thread is even created. It is
entirely possible the actual limit of Parameter 3 to repeat this behaviour is
much higher.
