Per the specs this is a doubly linked list. Here are the considerations that I
have made which go beyond the html spec doc.

- each function will print errors to console after being called from the main
  runner. Makaroff stated in lecture Sep 15 that he wants it to be verbose
  and doesn't care if it prints in phase3, so I'll leave all the printing in
  to help prove to the markers that it works

- we are told to "...check that the correct type and range of parameter values,
  as appropriate, have been passed between caller and calee...". As I understand
  you can't really get a function to execute without providing the right number
  of arguments. Every single parameter is a pointer for all the laid out
  functions, and as such I will simply ensure that NULL is not being passed.
  One exception is going to be comparisonArg, I can't assume that NULL is an
  invalid argument to comparator, and as such I will allow NULL to be passed.

- also, the instructions say the LIST will have a homogenous data type which I
  will document in the code, but that can't really be enforced other than
  telling the caller with words not to do it

- adders: ListCreate, ListAdd, ListInsert, ListAppend, ListPrepend, ListConcat
- movers: ListCount, ListFirst, Listlast, ListNext, ListPrev, ListCurr,
          ListSearch
- removers: ListRemove, ListFree, ListTrim

- the above choices prioritize "add" behaviour going in "adders", "remove"
  behaviour going in "removers", and the rest going in "movers" (including
  ListSearch and ListCurr per the spec). ListConcat and ListTrim do "move" the
  current spot in the list, but their add/remove behaviour is chosen to take
  precedence.

- the below was put in the Canvas by me, but outlines my decision when it comes
  to a few edge cases on return values (which might be a little "unexpected")

void *ListFirst(list) -> empty list case -> NULL return is fine and means "error
  no list"
void *ListLast(list) -> empty list case -> NULL return is fine and means "error
  no list"
void *ListCurr(list) -> current point has been backed out the front or stepped
  out the end of the list -> NULL return is fine and means
  "error no current item"
void *ListRemove(list) -> empty list case -> NULL return is fine and means
  "error no list"
void *ListRemove(list) -> current point has been backed out the front or stepped
  out the end of the list -> NULL return is fine and
  means "error no current item"
void *ListTrim(list) -> empty list case -> NULL return is fine and means "error
  no list"

- here are some other behaviours and how I choose to address them

LIST struct: count, pointer to head (first), pointer to tail (last), pointer to
  current item

NODE struct: pointer to item, pointer to next, pointer to prev

ListCreate -> will do the initial malloc() calls
ListCount -> will access item_count
ListFirst -> when empty curr == NULL
ListLast -> when empty curr == NULL
ListNext -> when advancing out curr == NULL
ListPrev -> when backing out the front curr == NULL
ListAdd -> calls node_get(). When curr == NULL, perform an append
ListInsert -> calls node_get(). when curr == NULL, perform a prepend
ListAppend -> calls node_get()
ListPrepend -> calls node_get()
For add/insert/append/prepend the return of -1 will only occur when there are
  no free nodes but since I'm doing the bonus, there will only be an error when
  the system errors on realloc()
ListRemove -> calls node_delete(). When curr == NULL no deletion will occur and
  curr will stay NULL
ListConcat -> calls list_delete() on list2.
ListFree -> calls list_delete()
ListTrim -> calls node_delete(). When empty, curr == NULL
ListSearch -> curr will be set to the head and walked down the list. It just
  gets left where it ends, and this is easier than creating a separate cursor

- there's going to be a global which is a boolean to track whether the LIST and
  NODE arrays have received their ONE initial malloc(). This will be checked by
  ListCreate() such that when False and when calling ListCreate(), the initial
  allocation will occur

- phase1 is this doc and the skeleton of each function, which will just check
  for NULL and then return to a main() function which will do fprintf() logs.
  list.h, list_adders.c, list_movers.c, mytestlist.c, and the Makefile

- phase2 I will create a test plan which covers many ways to break / validate
  the robustness of each function. The adders need to be implemented, but not
  the removers. I'm going to do the dynamic growth of the arrays. A counter will
  exist which tracks how many nodes are in use, and how many have been
  allocated. This allows for the available space to be treated as an array that
  I can use. When there are deletions, the last item in the block of array will
  be moved into that space so there's no gaps

- There are 4 main problems as far as I'm concerned

1 realloc() shifts the block of memory assigned to the NODEs / LISTs (maybe, or
  maybe not) and as such all the pointers become invalidated. Solution: they are
  shifted by a constant value, so go through all the chains and update the
  pointers by a constant value (new_ptr - old_ptr (could be negative))

2 when halving, using realloc() the above problem occurs but there is a new
  concern too. If half of the block of memory is going to be invalidated, no
  NODEs or LISTs must occupy that space. What this means is that, as deletions
  occur, the "gaps" produced in the block of memory being used must be "filled"
  and I will do this by copying the last entry in the block (tracked by idx
  already) into that space. If this is a NODE, the prev's next and the next's
  prev must be updated. All LISTs must be checked for the old pointer at the
  head, tail, or current, as that will also need updating

3 a LIST, during halving (or even doubling) is another can of worms. Say I am
  allocating from "2000", as an adress, and hand out 2000, 2001, 2002 as LIST
  pointers. After a realloc moving everything to, say, "1000", a user would
  come back with 2001 when they really mean the current 1001 list. We cannot
  update the user's pointer! The only thing I can think of doing is keeping a
  lookup table data structure (3rd malloc) that gets resized when LISTs get
  resized. It'll store user held pointers and program actual locations

4 solution 3 opens a new issue. Say a realloc now happens and sets it at "900".
  If we create the one-hundredth list, we'll hand out 1000 AGAIN. Solution: use
  the unused bits at the high end of the pointer since we're building on 64 bit
  systems there's space. These are tainted pointers and shouldn't be used
  directly, but since they are just keys to a real pointer, this is fine. If
  there is huge reuse, say 10-20, and 10,000 lists, you can't really search
  through all 10,000 lists, noting that 1, 2, 3, 4... are all free in turn. I
  will say that this isn't going to happen in our case, and I will implement
  it that way, but it would need to be made more efficient in real industry use

- I will make node_get(), node_delete(), and list_delete().
    NOTE: Makaroff just told me he wants node_double() / node_half() instead

  node_double() will be called when nodes_next_index == nodes_count (really >=
  but the > case means things are already broken) and if so it will realloc() a
  doubling in memory (nodes_count *= 2; malloc(nodes_count*sizeof(NODE))) and
  then go through all nodes (via indexing) and update each pointer (+= 
  new_block_ptr - old_block_ptr). It also needs to += head/tail/current of each
  list. At the end it will return node_block_ptr + next_node_index++;

  node_half() will be called when nodes_next_index == nodes_count / 2 (really <=
  but the < case means things are already broken). Note! my number will start as
  a power of 2, makeing sure that division by 2 is always an integer. This also
  only triggers when nodes_count > MIN_NODE_COUNT. It does the opposite of the
  above, and as such there must be no fragmentation

  list_double() does not exist, but will happen in the one function that gets
  lists. The lookup table will be doubled here too

  list_delete() is not called list_double because it also updates the lookup
  table that I'm going to be using
